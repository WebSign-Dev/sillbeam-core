# Sillbeam Core v0.4.0

These notes cover changes since the v0.3.0 tag. See the [changelog](../../CHANGELOG.md)
for the change list and the [upgrade guide](../migration/0.4.0.md) for deployment
and Composer steps.

## Public changes

- **Core Data API v1.** The `Sillbeam\Core\Api` PHP API and
  `sillbeam:api` share one architecture analysis. Live returns the catalog,
  diagnostics and references in one locale. Analysis adds structured graph data,
  a source inventory, Doctor checks, both available locales and a versioned
  fingerprint when the inputs and architecture evidence support one. The
  `sillbeam:api:capabilities` and `sillbeam:inspect:sources` commands expose
  capabilities and standalone inventory. See [Core Data and its schemas](../reference/core-data/README.md).
- **CLI language preferences.** Human-readable diagnostics support `en` and
  `de`, with a per-command override, a personal preference and a project
  default. The JSON commands use their documented locale rules. See
  [locale configuration](../reference/cli.md#locale-configuration).
- **Graph 2.0.** Native SVG uses deterministic dependency layers, scope bands and
  orthogonal routing. The existing filters, SVG file behavior and raw Mermaid
  export remain available. See the [graph reference](../reference/mermaid-graph.md).

## Lifecycle and consistency

Core architecture findings leave Symfony maintenance commands and Composer cache
scripts usable when the remaining application configuration can compile. Core
retains the findings and defers its graph-dependent registries, automatic services,
routes and Doctrine mappings. A production release needs both successful cache
preparation and a successful explicit architecture check. Production HTTP uses
prebuilt state. Without a compiled container, non-debug HTTP returns 503 before
source analysis. See the [lifecycle reference](../reference/architecture-analysis.md#development-and-production-lifecycle).

Missing required discovery roots and changes to already inspected, loaded
descriptors make analysis unavailable. Conventional discovery respects source link
boundaries. An Analysis export with detected input changes reports unknown
activation and omits the fingerprint. Core Data retains structured finding
evidence and omits free descriptor exception text. Review caller-supplied values
and legacy diagnostic context before sharing exports.

## Internal implementation

Core reuses the PHP parser and source-tree walks. The optional static parse cache
under `var/sillbeam/source-index` reuses results across processes when the source
content and parser inputs match. Invalid, unavailable or oversized snapshots
fall back to parsing. Compact debug resources reduce redundant Symfony
freshness checks. Symfony still controls container and route invalidation. See
[source index and cache invalidation](../reference/architecture-analysis.md#source-index-and-cache-invalidation).

The comparison with performance reference `d1070c1` used 100 generated modules,
five paired runs per environment and PHP 8.5.4. The baseline used Symfony
FrameworkBundle 8.1.6 and the reviewed runtime used 8.1.11. Median warm
HTTP follow-up requests moved from 7.87 to 7.60 ms in dev and from 3.75 to
3.67 ms in prod. The benchmark calls the kernel in-process and excludes network
time. Explicit architecture checks rose by about 4% in dev and 2% in prod.
Peak PHP allocation during `cache:clear` rose from 81.92 to 83.27 MiB in dev and
stayed at 62 MiB in prod. Median first dev requests moved from 282 to 315 ms
in the paired runs. A follow-up comparison with matching dependencies measured
385 vs. 386 ms and did not reproduce that gap. These are local fixture measurements.

## Compatibility and scope

The package, bundle, descriptor attributes, registries, configuration alias and
routing type carry forward from v0.3.0. Legacy Architecture and Doctor JSON
retain schema v1 and their exit-code meanings. Core Data has its own schema v1,
and the fingerprint algorithm carries a separate version. Doctrine is optional.
Core Data runs within Core and has no Hub, Connector or IDE-plugin dependency.

The declared requirements are PHP `^8.4`, Composer runtime API `^2.2` and Symfony
components `^7.4 || ^8.0`. Local QA covered PHP 8.4.26 and 8.5.4 with Symfony
FrameworkBundle 7.4.23 and 8.1.11. Symfony 8.0 could not be resolved with
Composer's security advisory blocking enabled. The development and reference-app
locks use patched Symfony versions.

Projects share their Symfony runtime and infrastructure. Architecture checking
covers supported static references within the discovery scope. Dynamic references,
arbitrary application behavior and tenant isolation are outside that scope.
When source or configuration changes during analysis, review the export's
completeness before relying on its graph or inventory.

## Local verification

Local QA for the reviewed runtime at `f54c8b3` recorded 726 PHPUnit tests per
matrix combination, static analysis, coding standards, Composer checks, schema
validation, independent consumers with and without Doctrine, local Flex scenarios
and ZIP installation checks. Local package tests used simulated version metadata.
